# Native components and interaction performance

Research snapshot: **September 10, 2026**. Applies to Relais at `688ad3a`, with Expo UI **57.0.17** and Expo Router **57.0.20**. This document complements the [code audit](native-code-audit-2026-09-10.md); it is a component-selection reference, not evidence that the proposed changes are implemented or benchmarked.

**Use native navigation and semantic SwiftUI/Material controls, preserve their default sizing and behavior, and keep continuous interaction local to the native UI where the installed binding supports it.** Retain React Native for shared product state and coordination. The priority is fewer unnecessary overrides and asynchronous round trips, not a wholesale rewrite.

## 2. What “native” means for this project

React Native primitives are platform-backed views; a RN `View` is not an HTML element on a phone. But choosing a primitive does not choose a complete platform control with its standard styling, selection model, menu placement and accessibility behavior. Relais should use **SwiftUI `Button`/`Picker`/`Form`** and **Compose Material `IconButton`/segmented buttons/sheets** for those purposes, through the existing bindings. RN containers remain appropriate for arranging native video and native hosts. [RN View](https://reactnative.dev/docs/view), [Expo UI](https://expo.dev/changelog/sdk-56).

SwiftUI/UIKit styling follows Apple frameworks and the linked SDK/running OS. Compose/Material is Google's native toolkit shipped as an app dependency; it does not become the proprietary Pixel Camera interface or every manufacturer's skin when Android updates. Material color, typography, shape and motion defaults provide the intended common language. [Apple Liquid Glass](https://developer.apple.com/documentation/technologyoverviews/liquid-glass), [Material 3 in Compose](https://developer.android.com/develop/ui/compose/designsystems/material3).

Selection order for new work:

1. Use the existing native navigation container or appropriate platform control.
2. Use its public style, slot, label, role and layout APIs before drawing replacements.
3. If the platform API exists but the installed Expo binding does not, identify the exact missing binding. Reuse an existing alternative or add a narrowly scoped Swift/Kotlin view in `modules/` when justified.
4. Compose custom native content only for a product-specific element without an appropriate public control. The existing shutter glyph inside a native button is a valid example. A private camera-app carousel is not a reason to rebuild all buttons, sheets or navigation.

The following facts were checked directly in `node_modules` from the pinned install; these are dependency-source observations, not claims about every Expo version.

| Capability                             | Installed source                                                                                                                                                              | Consequence                                                                                                                                                                                                                                     |
| -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Material Expressive and dynamic colors | `@expo/ui/android/src/main/java/expo/modules/ui/HostView.kt`: `MaterialExpressiveTheme`, `dynamicLightColorScheme`, `dynamicDarkColorScheme`; `android/build.gradle`: alpha17 | Already active through Host. Prefer `useMaterialColors()` and semantic roles outside the capture surface; adding another theme library is unnecessary.                                                                                          |
| Native draft state                     | `@expo/ui/src/State/useNativeState.ts`; `TextField` bindings on both platforms                                                                                                | `useNativeState` is already used by Relais device-name and connection fields. Preserve this. Initialization happens once per mount; changing the prop is not a reset. Handle switching the edited device/panel explicitly.                      |
| Synchronous toggle variants            | `swift-ui/SyncToggle/index.tsx`, `jetpack-compose/SyncSwitch/index.tsx`                                                                                                       | These exports accept observable state and UI worklet callbacks. Use only when a synchronous UI need warrants them. A visual toggle still cannot independently certify an applied camera configuration.                                          |
| Slider limitation                      | `swift-ui/Slider/index.tsx`, `jetpack-compose/Slider/index.tsx`                                                                                                               | Their current `value` is a **number**, not `ObservableState`. Android exposes `onValueChangeFinished`; iOS exposes `onEditingChanged`. Do not propose passing `useNativeState` to every slider or treating every callback as a UI worklet.      |
| Picker limitation                      | `swift-ui/Picker/index.tsx`, `jetpack-compose/SegmentedButton/index.tsx`                                                                                                      | Ordinary selected values/callbacks are used. | Bottom-sheet lifecycle                 | `jetpack-compose/ModalBottomSheet/index.tsx`                                                                                                                                  | `hide()` resolves after the dismissal animation. Reuse it for programmatic close before unmount where needed; user dismissal arrives through `onDismissRequest`. Keep the default grabber and gestures unless the active task requires a guard. |
| Native Router toolbar                  | `expo-router/build/toolbar/native.android.js`, `native.ios.js`; Router toolbar exports                                                                                        | The Android bottom toolbar uses Compose `HorizontalFloatingToolbar`; it is available, not a reason to draw a toolbar from Pressables. The public API is alpha and platform behavior differs.                                                    |
| Missing high-level bindings            | `@expo/ui/src/jetpack-compose/index.ts` and `swift-ui/index.tsx`                                                                                                              | Current barrels do **not** export Compose `Scaffold`/`TopAppBar`/`SupportingPaneScaffold` or SwiftUI `NavigationStack`/`ToolbarItem`. Use Router's navigation or the existing native Swift view; do not invent these imports.                   |

Expo's observable state maps to native SwiftUI/Compose state without requiring a React render. UI worklet writes are synchronous; JS-thread writes are scheduled asynchronously. Prefer `.get()`/`.set()` when writing compiler-compatible code, and clean up any native state listener. This is appropriate for UI feedback, not blocking I/O or invoking arbitrary camera methods from a worklet. [Expo native state](https://docs.expo.dev/versions/latest/sdk/ui/swift-ui/usenativestate/), [TextField behavior](https://docs.expo.dev/versions/latest/sdk/ui/swift-ui/textfield/).

`Stack.Toolbar` supports header and bottom placements, but Android spacers require an explicit width, Android label/search-slot behavior differs from iOS, and bottom toolbars belong to screen components. Use the native default Back item and restrict initial adoption to straightforward actions. Do not assume its newer toolbar API resolves the existing Android crash. [Expo toolbar constraints](https://docs.expo.dev/router/advanced/stack-toolbar/).

## 5. Apple conventions: adopt the system's treatment

**Materials and geometry.** Liquid Glass belongs primarily to controls/navigation above content. Keep the video as content; avoid applying glass to every card or nesting multiple glass backgrounds. Prefer native `.glass`/`.glassProminent` button styles on supported OS versions rather than recreating a material with blur, shadows and a custom radius. Let standard spacing and control sizes adapt. [Apple materials](https://developer.apple.com/design/human-interface-guidelines/materials), [Liquid Glass adoption](https://developer.apple.com/documentation/technologyoverviews/adopting-liquid-glass).

**Sheets.** Medium/large detents support progressive disclosure, while a QR or larger task can warrant a large sheet. Preserve the grabber, standard dismissal and keyboard adaptation. Use Cancel/Close for dismissal and Done/Save for completing the corresponding task; a Back action belongs to a hierarchy. A sheet already presented by SwiftUI does not need a second Router `formSheet` wrapper. Unsaved input and an active recording have different dismissal consequences. [Apple sheets](https://developer.apple.com/design/human-interface-guidelines/sheets).

**Type and icons.** Use semantic text styles, SF Symbols and native label roles. Important icons should scale with text; fixed-size icon wrappers need deliberate treatment at accessibility sizes. Use a system symbol's appropriate weight/rendering instead of embedding a screenshot of it. New symbols require fallback for older OSes. [Apple typography](https://developer.apple.com/design/human-interface-guidelines/typography), [SF Symbols](https://developer.apple.com/design/human-interface-guidelines/sf-symbols).

**Touch and accessibility.** Keep Relais's comfortable **44pt** iPhone target policy and larger shutter. The current HIG distinguishes a 44pt default from a smaller minimum; do not confuse a project ergonomics rule with an unconditional OS API requirement. Preserve spacing, accessible labels/values, alternate visible actions and reduced-motion behavior. [Apple accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility).

**Newer toolbars.** The iOS 27 documentation introduces toolbar visibility priorities, overflow grouping and pinned trailing placement. Those are useful future tools for keeping critical actions accessible as space changes. Compile them only with a compatible SDK; keep the shutter visible rather than applying auto-minimizing navigation behavior indiscriminately to capture. [SwiftUI toolbar updates](https://developer.apple.com/videos/play/wwdc2026/269/).

**Camera Control offers actual system UI.** `AVCaptureSystemZoomSlider` and `AVCaptureSystemExposureBiasSlider` supply Apple's controls for the hardware Camera Control experience. Their ranges follow the active device format. They are available in the installed headers from iOS 18, with session `supportsControls`/`canAddControl` checks. They are not general inline SwiftUI sliders or a replacement for the entire camera screen. Integrate them into `AppleCameraModel` only after the lifecycle fixes, and synchronize changes with its effective settings. Hardware Rec/Stop remains a separate AVKit event path. [Apple Camera Control integration](https://developer.apple.com/documentation/avfoundation/enhancing-your-app-experience-with-the-camera-control).

## 6. Android conventions: Material behavior, state and window integration

**Use theme roles and component defaults.** `primary`, `onSurface`, `surfaceContainer` and typography roles preserve relationships across light/dark and dynamic color. Material Expressive is more than a rounded shape: its theme coordinates components and motion. Keep the capture surface neutral with explicit recording feedback; avoid hardcoded decorative colors on every settings row. The existing Expo Host already provides the expressive theme. [Material 3 theming](https://developer.android.com/develop/ui/compose/designsystems/material3).

**Use the Material component matching the interaction.** An exclusive selector is a segmented row or radio group, an action is a button, and a boolean setting is a switch. Retain built-in disabled/selected semantics, minimum **48dp** touch areas and native ripple/focus behavior. Icon-only actions need a useful content description; decorative icons should not be announced twice. [Compose accessibility defaults](https://developer.android.com/develop/ui/compose/accessibility/api-defaults).

**Let a sheet finish its lifecycle.** `ModalBottomSheet` handles its presentation and dismissal gestures. For an explicit close, hide it and then remove it from composition. A native dismissal callback can clear the presented state directly. Maintain one active sheet and keep camera/session ownership outside the sheet's lifetime. [Compose bottom sheets](https://developer.android.com/develop/ui/compose/components/bottom-sheets).

**Assign one owner to each inset.** Protect controls from navigation gestures, cutouts and keyboards, while allowing the video background to extend edge-to-edge. Compose insets animate with the keyboard. `Scaffold` content padding must be applied/consumed appropriately; do not apply RN safe-area padding and native system padding to the same edge without accounting for both. In a mixed RN/Compose screen, document which layer owns each edge. [Compose insets](https://developer.android.com/develop/ui/compose/system/insets-ui), [Material Scaffold](https://developer.android.com/reference/kotlin/androidx/compose/material3/Scaffold.composable).

**Keep native Back in control.** Default navigation should own idle Back and predictive transitions. Enable interception only for the state that requires a confirmation; let the sheet consume its own dismissal first. Do not add an independent Compose back handler beside Router merely because the API exists. This follows the already identified camera-route fix. [Android Back guidance](https://developer.android.com/guide/navigation/custom-back/predictive-back-gesture).

**Adapt to the available window, not the phone's marketing model.** Window size and posture can change while the app runs. `currentWindowAdaptiveInfo()` and supporting-pane patterns describe the native direction; the current binding does not export every adaptive container. Start with the existing route's available dimensions, then add a narrow native adaptive surface if the product needs it. Do not confuse window-width layout breakpoints with the OS target-37 `sw ≥ 600dp` behavior rule. [Window size classes](https://developer.android.com/develop/adaptive-apps/guides/use-window-size-classes), [Android 17 behavior](https://developer.android.com/about/versions/17/behavior-changes-17).

## 7. Practices that matter for responsiveness

1. **Keep navigation transitions and stock gestures native.** Native-stack transitions do not depend on JS producing every animation frame. A busy native UI thread can still stutter; native rendering is not a blanket performance guarantee. [RN performance](https://reactnative.dev/docs/performance).
2. **Separate draft, requested and applied state.** Native text entry owns its draft; shared JS coordinates commands; the camera owner confirms effective hardware state. A responsive checkbox must not turn “HDR requested” into “HDR applied” before native validation.
3. **Keep continuous controls cheap.** The Android exposure slider currently calls `props.onExposure` continuously in [CameraOptions.android.tsx](../../src/components/CameraOptions.android.tsx#L152). Preserve responsive exposure feedback, but avoid routing every sample through a whole-session reconfiguration, persistence or large screen render. Commit expensive operations at interaction end when appropriate; coalesce continuous hardware updates at the native boundary if needed. The iOS camera already uses native SwiftUI state and AVFoundation.
4. **Use native state selectively.** Preserve the existing native text-field drafts in [DeviceList.ios.tsx](../../src/components/DeviceList.ios.tsx#L110), [DeviceList.android.tsx](../../src/components/DeviceList.android.tsx#L82) and connection sheets. Do not add worklets to low-frequency buttons or pass observables to unsupported slider props. Reinitialize drafts deliberately when the edited entity changes, without resetting an active cursor on unrelated renders.
5. **Keep host layout coherent.** Give flexible controls a finite width. Do not apply `matchContents` on the scrolling axis of a SwiftUI scroll container; it can remove the viewport needed for scrolling. Use `RNHostView` at an intentional RN-inside-native boundary, such as the QR; it measures one direct child, so group multiple RN children inside a parent view. Avoid changing the camera view's identity to refresh a nearby label. [Expo Host sizing](https://docs.expo.dev/versions/latest/sdk/ui/swift-ui/host/), [RNHostView](https://docs.expo.dev/versions/latest/sdk/ui/swift-ui/rnhostview/).
6. **Do less work during rendering.** Keep blocking storage, network operations and capture configuration out of UI callbacks/render bodies. Preserve stable identity in lists and avoid propagating rapidly changing state through an entire screen. In native Compose code, use `remember`, stable lazy-list keys and narrowly placed state reads where they solve a measured issue. Do not blanket-memoize or rewrite everything for compiler optimization. [Compose performance practices](https://developer.android.com/develop/ui/compose/performance/bestpractices).
7. **Let standard controls own their motion.** Do not add competing React animations on top of native sheet, slider or button transitions. Native custom motion should use platform theme/animation APIs and accessibility preferences. No artificial wait, full-screen spinner or per-frame JS timer should gate access to an already-ready camera.
8. **Preserve separate performance budgets.** UI refresh, camera file fps, preview fps and network latency measure different things. Keep video buffers native and main-thread camera work off the interaction path. Only an optimized physical-device measurement can establish the actual gain; this research pass makes no 120Hz or startup-time claim. [Existing budgets](../energy-and-perf.md), [RN release-mode measurement](https://reactnative.dev/docs/performance).

## 8. Practical adoption order

This refines the existing audit backlog without changing its recording-first order.

| Step                      | Specific application                                                                                          | Expected benefit / proof                                                                                                                                |
| ------------------------- | ------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Preserve                  | Existing native Home, segmented controls, sheets, device drafts, native icons and pinned dependency versions  | Avoid rewriting already-correct native behavior. No implementation needed solely to rename a component.                                                 |

## 9. Research maintenance and verification

For the next component change, check the official guide, its API reference/availability, and the installed `.tsx`/Swift/Kotlin implementation. Prefer the actual current page over an older search snippet. For example, the live Xcode table in this pass listed RC while an indexed result still listed beta 4. Likewise, the latest Material reference's version annotation is not evidence that an older experimental implementation is missing from the installed Host.

Use versioned Expo documentation for implementation where available and annotate `latest` references with the installed version verified here. Keep source links next to the decision. Add a new dependency only for a demonstrated public-API gap. All durable native changes belong in modules/config plugins, not generated projects.

This pass checked source/API compatibility and documentation links. It did not change production code, upgrade packages, run native builds or perform visual QA. Future changes should use the existing focused checks; the owner handles appearance and gesture inspection. Run a native rebuild only for an actual native/dependency change, and measure performance only when a specific unresolved issue calls for it.
