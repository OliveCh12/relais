# Product foundation: decisions, delivered changes and release gates

September 11, 2026. Source review based on `6c121d2` and the follow-up changes recorded in STATUS. This is a product/architecture assessment, not a claim of completed field certification.

## Product contract

Relais turns one phone into a camera and another into its controller. The camera phone owns the sensor, active settings, recording lifecycle and original files. Both phones can change the camera's supported settings. Monitor keeps a simple preview with photo/start/stop, focus and brightness, plus direct access to Camera Settings for the named camera. Preview framing belongs to Monitor and cannot change the original file.

The local camera uses platform presentation: SwiftUI/AVFoundation on iOS, Compose/CameraX on Android. Monitor shares behavior and layout semantics, while keeping native navigation, icons and settings controls. Do not duplicate the application by OS, and do not force the two camera engines into the same list of hardware features.

“All settings” means all implemented and publicly accessible capabilities advertised by that camera. It does not mean every mode found in the manufacturer's camera app, arbitrary combinations, or changing an encoder format halfway through a recording. Focus, exposure compensation, zoom and grid may remain available during recording; resolution, cadence, HDR, camera switching and microphone configuration require an idle camera. The UI should explain when a control can be changed, rather than hiding the entire settings page.

## Hardware identification is not capability detection

The user-chosen pairing name identifies a remembered phone. Native manufacturer, model and OS version identify its hardware/software context. Neither is a sufficient rule for enabling a recording format. Android now reports `Build.MANUFACTURER`, `Build.MODEL` and `Build.VERSION.RELEASE`; iOS reports Apple, its system model identifier and `UIDevice.systemVersion`. No serial number, advertising ID, IMEI or model-to-resolution lookup is needed. The information is sent only through the existing paired camera state and cached with it. [Android Build](https://developer.android.com/reference/android/os/Build).

The active lens/session must still advertise supported combinations. The same phone can have different limits on its front camera, telephoto camera, HDR mode, stabilization or simultaneous preview outputs. A public, locally recordable 8K profile should be exposed once the engine can validate and record it. Google's documented Pixel 8K workflow instead uses Video Boost and cloud processing in Google Photos; no public Video Boost capture API was found in the reviewed camera APIs. [Google Video Boost](https://support.google.com/pixelcamera/answer/14257322?hl=en).

The existing original-file and reduced-preview split is the correct direction. It is not complete independence from hardware stream-combination limits: CameraX explicitly warns that adding ImageAnalysis/ImageCapture can invalidate otherwise supported Preview/VideoCapture combinations. [CameraX capture architecture](https://developer.android.com/media/camera/camerax/video-capture).

## Concrete changes in this follow-up

1. **One settings command contract on Android.** Local Camera Settings now uses the same presentation model and validated `CaptureAction` path as Monitor, including native completion. Separate setters for local profile, microphone and stabilization were removed from the UI-facing engine interface. The iOS SwiftUI owner keeps its platform controls and applies local/remote changes through the same native model.
2. **Presentation separated from control.** The settings-section builder moved from `src/capture/` to `src/components/cameraSettingsSections.ts`. Boundary checks reject presentation imports in the shared control layer. Native frame processing remains outside JS.
3. **Configuration dependencies made explicit.** `settingPolicy.ts` records which settings are live adjustments, which invalidate the format catalog, and the ordering of preset changes. Presets apply mode, camera position and stabilization before selecting a format; each step reads the newly acknowledged state. Previously, format selection ran before stabilization, which could reject a high-rate profile that would become valid with stabilization disabled.
4. **Optimistic controls remain bounded.** A stabilization change invalidates the projected format catalog until the camera confirms a new one. It also separates coalescing batches, just like a mode/lens change. Queued controls cannot be merged across that dependency boundary.
5. **Hardware context is visible.** Device → Connection includes the camera's manufacturer, hardware model and OS version. The optional state field remains compatible with older peers that omit it. Metadata does not enable extra formats by itself.
6. **Shorter Monitor path.** Its Settings button opens the connected device's Camera Settings directly. Device identity, pairing and network information remain available from My cameras.

7. **Priority Stop on both monitors.** `RemoteCommandClient` owns dispatch, request identity, deadlines and the settings queue. Stop/cancel bypass ordinary adjustments, cancel unsent values and share the same pending request across repeat taps. Late replies cannot complete a replacement request or overwrite its state. iOS tags asynchronous adjustment callbacks with an operation ID before allowing Stop to supersede focus/exposure/zoom or recording startup. Android already dispatches Stop independently through `RecordingController`, which waits for native finalization and MediaStore completion. Neither path treats disconnection as a request to stop recording.
8. **Focused cleanup.** Removed the duplicate pending-request bookkeeping from `useConnection` and the unused queue reconfiguration method. The historical stub and isolated development spike still have callers and explicit project requirements; they remain separate from the production camera owners.

Tests cover the baseline behavior, identical commands from local/remote settings, record-time editability, large/native-supplied profile choices, dependency ordering, abort after native failure, and metadata validation. Native compilation and physical capture validation remain separate evidence.

Autonomous rendezvous remains the open P0 item. Stop preemption is now implemented in code and covered by command/queue regression tests and native compilation; Stop during a physical recording remains owner-run acceptance. Install both updated builds, because an older iOS camera still has the previous single-operation gate.

For LAN discovery, use standard interoperable mechanisms rather than an Apple-only transport or a separate Android-only control protocol. Apple provides native listeners with Bonjour advertisement; Android provides NSD. At target SDK 37+, Android local-network access has a permission/system-picker model that must be handled before opening sockets; do not rely on the permissions already granted on the development phone. These references support the proposed direction, not a tested Relais implementation. [Apple NWListener](https://developer.apple.com/documentation/network/nwlistener), [Android NSD](https://developer.android.com/develop/connectivity/wifi/use-nsd), [Android local-network permissions](https://developer.android.com/privacy-and-security/local-network-permission). The September 11 recheck confirms that SDK 36 and lower retain implicit LAN access; do not add the new SDK 37 permission before targeting that version.

## Capture quality and engine choice

Keep AVFoundation on iOS. Keep the current native CameraX engine while it satisfies the validated recording modes. Replace or extend the Android adapter with direct Kotlin CameraX/Camera2 only when a required public capability is demonstrably inaccessible through the current wrapper. This preserves pairing, Monitor and media transport while the capture implementation evolves. No full camera rewrite or dependency upgrade is justified by a phone model name alone.

“Maximum resolution/FPS” is an explicit preference, not a promise of better images in every situation. Higher cadence can reduce available exposure time and increase storage/thermal cost. Preserve user choices and let the native camera run autofocus/exposure/white balance. Keep advanced formats in settings; keep the viewfinder focused on framing and capture. Do not continuously override the camera's chosen settings from the Monitor.

## Next release boundary

A credible standalone LAN release requires autonomous rendezvous and owner-run proof with only two phones: no laptop, no Metro, no manual server address. It must keep local capture safe through remote edits/disconnects and confirm that originals arrive in the camera phone's gallery. A source-controlled matrix should distinguish public native support, Relais implementation, supported relay combinations and physically verified output. “Not supported”, “not implemented”, “temporarily unavailable” and “not yet tested” are different states.

Prioritize that release boundary before adding more camera modes. The present changes strengthen the control/settings foundation; [STATUS](../STATUS.md) records their actual build and installation evidence, and the [platform-camera decision](research/platform-camera-architecture.md) covers current native API limits.
